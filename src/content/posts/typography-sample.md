*这是一篇用来检查排版的示例文章，内容是占位的。写了第一篇真正的文章之后可以把它删掉。*

很多想法待在脑子里的时候，看起来是完整的。直到试着把它写下来，才发现中间缺了好几步。Writing 不只是表达的工具，它本身就是**思考发生的地方**。[^1]

所以我更愿意把一篇文章看成一次 [debugging](https://en.wikipedia.org/wiki/Debugging)：你带着一个模糊的直觉开始，写到一半被自己的句子反驳，然后回头修改前提。这个过程*并不舒服*，但它是唯一可靠的检查。

> 写不清楚，多半是还没想清楚。

## 三个步骤

我现在写东西大致分三步：

1. 先用一句话写出结论，写不出来就先不动笔。
2. 把最强的反对意见写出来，看结论还站不站得住。
3. 删掉所有“显然”和“众所周知”。

每一步关心的东西不一样：

| 阶段 | 目标 | 可以先不管 |
| --- | --- | --- |
| 草稿 Draft | 把想法倒出来 | 措辞、结构 |
| 修改 Revise | 找出缺的那几步 | 文采 |
| 定稿 Final | 让别人读得懂 | — |

## 技术文章也一样

一段解释不清楚的代码，通常是因为自己还没有想清楚它在做什么。比如一个 `debounce`，写之前先用一句话说出它的行为：

- 连续触发时不执行；
- 停下来超过 `wait` 毫秒，才执行最后一次。

```js
// 停止触发 wait 毫秒后，才执行最后一次
function debounce(fn, wait = 200) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  };
}
```
